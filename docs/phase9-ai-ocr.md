# HealthVault medical OCR and AI intelligence

## OCR implementation

OCR is configured with `OCR_PROVIDER=tesseract`; it remains disabled by default. The backend processes only patient-owned private PDF, JPEG and PNG objects, verifies their recorded checksum before processing, and leaves the source file unchanged. PDFs first use PDF.js digital text extraction, with page-by-page Tesseract OCR fallback when digital text is absent. Processing is limited to 12 pages and 200,000 characters; retry attempts are capped at three. OCR output is explicitly unverified. Patients can edit extracted text and structured result rows, and the saved patient review is kept separately from the extraction.

Set `OCR_LANGUAGES=eng` (or a supported installed language code). Tesseract.js needs its traineddata files available to its worker; first-run downloads may require internet access. For isolated deployments, provision language data in a private local directory and set `OCR_LANG_PATH` to that directory. Handwriting support has not been tested and is not claimed. PDF scans beyond the page, pixel and upload size limits are rejected.

Migrations `20261119103000_document_ocr_results` and `20261119130000_document_ocr_metadata` add one OCR result per document, linked to the patient profile and optional reviewing user. Extracted and patient-reviewed report metadata (patient name, date, lab and comments) are stored separately from the original. OCR values are not included in sharing responses. The AI assistant receives only patient-reviewed OCR from that patient's own available documents and only after active AI data-processing consent is verified for the request.

## Medical AI and report intelligence

The existing OpenAI integration stays backend-only and disabled until `AI_ASSISTANT_ENABLED=true`, `AI_ASSISTANT_PROVIDER=openai`, `OPENAI_API_KEY` and patient consent are all present. Questions use only the authenticated patient's profile, recent readings and owned report metadata/reviewed OCR. Unreviewed OCR and source files are excluded. The prompt treats records as untrusted, forbids instructions embedded in records, requires uncertainty and citations, and disallows diagnosis or medication changes. The provider returns generated educational explanations, not clinically verified conclusions.

The modular RAG foundation is implemented with versioned `MedicalKnowledgeSource` and `MedicalKnowledgeChunk` records. Migrations `20261119120000_medical_knowledge_rag` and `20261119140000_knowledge_embedding_model` add the schema. An authorized existing `ADMIN` can inspect `GET /api/admin/medical-knowledge/status` and ingest reviewed text through `POST /api/admin/medical-knowledge/sources`. Ingestion requires a source title/name, HTTPS URL on an allowlisted WHO, MedlinePlus, NIH or NCBI domain, license/permission description, version and text; it creates bounded overlapping chunks and backend OpenAI embeddings. Duplicate source versions are rejected and importing a new version switches the prior version off for retrieval. Query embedding and cosine ranking retrieve up to four matches from the current embedding model (maximum 2,000 chunks scanned); responses include source name, URL and version. Source text is treated as untrusted prompt context. The endpoint does not scrape websites, verify licensing, or certify the medical content, so administrators must review source and reuse rights before importing it.

No knowledge source has been ingested in this environment. RAG is therefore implemented but returns no medical knowledge citations until reviewed, licensed material is imported. `OPENAI_API_KEY` is required for embeddings; use `AI_ASSISTANT_EMBEDDING_MODEL` only with a clean re-ingestion or matching existing model. No previous AI conversations are retrieved or retained.

Structured trends currently available to the assistant are the patient's recorded blood pressure and glucose readings, with dates and units. Glucose comparisons group only matching measurement units and measurement types. Laboratory parameter trends require at least two patient-reviewed OCR results with the same test label and compatible units; no lab value is inferred from an unreviewed scan. A label mismatch can prevent a valid comparison. These are arithmetic comparisons, not diagnoses or clinical significance assessments.

## Verification boundaries

Use synthetic reports for automated tests. The automated OCR test exercises digital PDF text and structured value parsing; it does not validate scanned image OCR or traineddata availability. Real OCR tests require language data and should verify scanned PDF fallback, JPG/PNG, multi-page handling, malformed documents, false extraction and retry limits. The synthetic similarity test validates RAG ranking/source attribution; it does not test a live OpenAI embedding call or medical source quality. Real OpenAI tests require an explicitly approved isolated account and synthetic records. Never test external processing with real patient data.
